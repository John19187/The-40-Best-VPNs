# 维护与测试方法

本文档定义服务商资料、链接检查和性能测试的最低证据标准。目标是让第三方能够复核
结论，而不是把服务商宣传语当成独立测试结果。

## 数据来源分级

每条信息按以下优先级记录：

1. **可复现实测**：包含日期、地区、网络、客户端、协议、结果和去敏证据。
2. **公开一手来源**：服务商官网、状态页、价格页或正式公告。
3. **社区报告**：GitHub Issue 或 Pull Request 中可核查的复现记录。
4. **服务商声明**：尚未独立验证，只能标记为 `vendor_claims_only`。

无法确认的字段必须使用 `null` 或 `unknown`，不得根据宣传文案推断。

## 服务商状态

`data/providers.yml` 是服务商清单的结构化事实源：

- `active`：最近一次检查可以正常访问，且没有可靠停运证据。
- `inactive`：官网明确停运，或多个独立来源证明服务已经终止。
- `unknown`：尚未检查、被反爬拦截、网络超时或证据不足。

自动链接检查只更新报告，不自动把 `unknown` 改成 `active`。HTTP 成功仅表示页面当时
可达，不代表服务质量、隐私政策或付款安全。

## 链接检查

`scripts/check_links.py` 对 `providers.yml` 中存在 URL 的条目执行以下步骤：

1. 先发送带明确 User-Agent 的 HEAD 请求。
2. 站点不支持 HEAD 时，退回只读取少量响应内容的 GET 请求。
3. 跟随标准 HTTP 重定向并记录最终 URL、状态码与耗时。
4. 404 和 410 记为 `broken`；401、403、405 和 429 记为 `blocked`；网络错误和
   5xx 记为 `error`，避免把临时故障直接判成停运。

检查结果写入 `.artifacts/link-check.json`，该目录不进入版本控制。GitHub Actions
每周运行并保存报告工件。

## 性能测试

性能数据追加到 `data/test-results.csv`。一次有效测试至少需要记录：

- 测试日期和大致地区；
- 网络运营商或网络类型；
- 客户端版本与连接协议；
- 延迟、下载、上传和丢包中的至少一项；
- 流媒体或 AI 服务解锁的具体测试对象；
- 去除账号、IP、订阅链接后的证据地址。

同一服务商应尽量在相同时间段重复至少三次。测试结果只代表特定地区、网络和时间，
不能外推成“始终稳定”“绝对匿名”或“保证解锁”。

## 商业关系

每个服务商必须在 `commercial_relationship` 中声明关系：

- `affiliate`：链接或邀请码可能产生佣金、返利或积分。
- `sponsored`：服务商提供了费用、免费套餐或其他对价。
- `none`：维护者确认不存在直接利益关系。
- `undisclosed`：尚未由维护者确认，不能解释为“没有利益关系”。

是否存在商业关系不能单独决定排名。发生关系变化时，应同时修改结构化数据、README
披露和相关评测说明。

## 排名与修正

排名或推荐结论应能追溯到公开标准和证据。收到有证据的纠错后，通过 Issue/PR 留下
记录；重大状态变化写入 README 更新日志或 GitHub Release。禁止购买 Stars、伪造测试、
批量创建无实质内容的贡献或用多个账号制造社区活跃度。
